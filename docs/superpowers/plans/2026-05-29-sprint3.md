## Part A — Messaging integration

### Task A1 — hermes recipient capability (RESOLVED 2026-05-29)

**Decision (settled — no action needed):** `hermes send -t` supports per-chat targeting:
`-t '<platform>'` (home channel), `-t '<platform>:<chat_id>'`, `-t '<platform>:<chat_id>:<thread_id>'`, or `-t '<platform>:#channel-name'`. Verified via `hermes send --help`.

Consequence for Task A3: `chat_id` is **threaded through** as `-t "<platform>:<chat_id>"` when present, falling back to bare `<platform>` when absent. The current code's bare `-t telegram` is a wrong-recipient bug on the gateway path (replies land in the home channel, not the originating chat).

### Task A2 — Make `tts-feed-send.py` the sole delivery owner with opt-in egress

**Files:** Modify `scripts/tts-feed-send.py`

- [ ] **Step 1: Add a `send_to` resolver**

Add a function that returns the set of enabled platforms from (in priority order): env `AFTERWORDS_SEND_TO` (comma-separated), then a `send_to:` line in `$PWD/.afterwords`, then `$HOME/.afterwords`. Default: empty set (no external send). Accept only `telegram`, `discord`.

- [ ] **Step 2: Gate `process_new_files` on the resolved set**

Before any `send_media(...)` call, skip platforms not in the enabled set. When the set is empty, mark files seen (so they don't accumulate) but send nothing; print `  [skip] <name> (no send_to configured)`.

- [ ] **Step 3: Verify with dry-run and empty config**

```bash
AFTERWORDS_SEND_TO="" python3 scripts/tts-feed-send.py --once --dry-run
AFTERWORDS_SEND_TO="telegram" python3 scripts/tts-feed-send.py --once --dry-run
```

Expected: first sends/queues nothing for external delivery; second shows telegram-only in the dry-run preview.

### Task A3 — Remove inline send blocks from the hook

**Files:** Modify `scripts/afterwords-post-llm.sh`

- [ ] **Step 1: Remove the CLI tail send block** (lines ~239–283, the `# ── CLI: Also send audio to Discord/Telegram ──` section). The CLI path ends after local playback + archive.

- [ ] **Step 2: Keep one guarded inline send in the `MSG_PLATFORM` branch** so inbound replies reach the originating chat: `hermes send -t "<platform>:<chat_id>"` (bare `<platform>` when `chat_id` empty). Ensure the watcher does **not** also send these — pre-seed `tts-feed-seen.json` for the inline-sent stem, or write the inbound archive to a non-watched path. (See design Problem 1 de-dup requirement.) The invariant: exactly one delivery per response per platform.

- [ ] **Step 3: Thread `CHAT_ID` into the send target.** Wherever a guarded `hermes send` survives (and in `tts-feed-send.py` if it gains access to the originating chat), build the target as `"<platform>:<chat_id>"` when `chat_id` is non-empty, else bare `"<platform>"`. Note: `tts-feed-send.py` works off archived files and has no `chat_id` context, so per-chat reply is only achievable on the inline hook path — if egress moves entirely to the watcher (Task A2), gateway replies go to the home channel. **Sub-decision for the implementer:** keep a single guarded inline `hermes send -t "<platform>:<chat_id>"` in the `MSG_PLATFORM` branch for correct inbound replies, and use the watcher only for the CLI (outbound, no originating chat) path. This splits ownership cleanly by direction rather than duplicating.
